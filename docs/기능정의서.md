### F-03 월 진행

- 담당: 팀원 1
- 화면: 팀원 3(월 진행 버튼, 월말 보고 창)
- 관련 API: `ProgressSystem.start()`, `endMonth()`, `nextMonth()`, `canAdvance()`
- 기준: 기획서 5.1

**상태 값**

날짜는 `{ month, phase }`로 관리한다.

- `PLAN`: 월초 계획
- `RUN`: 업무 진행
- `REPORT`: 월말 보고

**동작**

1. 월초 계획에서 이번 달 요청과 집행 가능액을 확인하고 필요한 확인 작업을 끝낸다.
2. 월 진행 명령을 실행하면 해당 월의 업무가 진행된다(`RUN`).
3. 진행 중 사건이 발생하면 시간이 멈추고 플레이어에게 대응을 요청한다. 대응을 마치면 같은 달의 남은 진행을 이어간다.
4. 월말이 되면 완료·미해결 업무와 다음 달 할 일을 보고한다(`REPORT`).
5. 보고를 닫으면 다음 달 월초 계획으로 이동한다.

**규칙**

- 시간은 월 진행 명령으로만 흐른다. 현실 시간이나 미접속 시간으로 진행하지 않는다.
- 월 진행 한 번에 정확히 한 달의 업무를 처리한다.
- 진행 중, 사건 대응으로 멈춘 상태, 월말 보고 중에는 다음 월 진행 명령을 실행할 수 없다.
- 첫 버전은 2개월이다.

**예외**

- 월초 확인 작업을 끝내지 않았으면 월 진행 버튼을 비활성화하고 이유를 표시한다.
- 진행 중 사건이 해결되지 않았으면 다음 달로 넘어가지 않는다.

**완료 조건**

- 월 진행 버튼을 빠르게 두 번 눌러도 한 번만 처리된다.
- 사건으로 멈춘 상태에서 다음 달로 넘어가지 않는다.
- 1월차 → 2월차 → 튜토리얼 종료 순서가 지켜진다.

## 3. 1월차: 요청 확인과 계약

### F-04 요청서 확인

- 담당: 팀원 1(사업 데이터, 확인 처리)
- 화면: 팀원 3
- 기준: 기획서 4장 진행 단계 '요청 확인', 판단 포인트 '사용자 규격'

**데이터**

- 사업(Project)
- 요청기관은 학당이다.
- 대상은 강당에 머무는 주민 약 20명의 매트와 침구다.

**동작**

1. 요청서에는 미확인 항목이 있다: 주민 수·연령 구성, 사용자 규격.
2. 플레이어가 각 항목을 확인하면 해당 정보가 공개된다.
3. 사용자 규격은 요청기관에 확인한다. 아동·고령자용 규격이 별도로 필요한지 드러난다.
4. 첫 확인을 하면 사업 단계가 `REVIEWING`으로 변경된다.

**화면 표시**

- 계약 방식
- 평가 기준
- 검수 책임 주체

기획서 5.2의 기준을 따른다.

**미정**

- 연령 구성 수치
- 사용자 규격 확인 결과와 필수 추가 규격

**완료 조건**

- 주민 정보와 사용자 규격을 모두 확인해야 F-05의 부족 수량 확정이 가능하다.

### F-05 재고 확인과 부족 수량 확정

- 담당: 팀원 1
- 화면: 팀원 3
- 힌트: F-15
- 기준: 기획서 4장 '재고 확인', 판단 포인트 '재고 상태'

**시작 값**

- 매트 재고 8개
- 침구 재고 12세트

기획서 4장의 초기 재고를 기준으로 한다.

**동작**

1. 매트와 침구의 재고 수량을 확인한다.
2. 매트 상태를 점검하면 젖은 매트 수가 드러난다. 상태 점검은 선택이다.
3. 사용 가능한 재고를 기준으로 부족 수량을 계산한다.
4. 부족 수량을 확정하면 계약 수량으로 사용한다.

**계산 규칙**

- 매트 사용 가능 수량 = 전체 매트 재고 − 젖은 매트 수
- 매트 부족 수량 = 주민 수 − 매트 사용 가능 수량
- 침구 부족 수량 = 주민 수 − 침구 재고 수량
- 부족 수량이 0보다 작으면 0으로 처리한다.
- 매트 상태를 점검하지 않으면 젖은 매트를 정상 재고로 간주한다. 따라서 실제보다 매트 부족 수량이 적게 계산될 수 있다.

**예외**

- 매트 상태를 점검하지 않고 부족 수량을 확정하려 하면:
  - 힌트가 켜져 있을 때 달이가 한 번 안내하고 확정을 보류한다.
  - 다시 확정하면 점검하지 않은 상태의 재고를 기준으로 확정한다.
  - 힌트를 꺼 두면 안내 없이 확정한다.
- 상태 점검을 생략한 판단 실수는 이후 검사 단계에서 드러날 수 있다. 구체적인 보완 방식은 기획 확정 전까지 임의로 정하지 않는다.

**미정**

- 젖은 매트 수
- 부족 수량을 잘못 확정했을 때 이후에 어떻게 드러나고 보완하는지

**완료 조건**

- 상태 점검 여부에 따라 매트 사용 가능 수량과 부족 수량이 다르게 계산된다.
- 침구 부족 수량은 침구 재고를 기준으로 계산된다.
- 힌트는 한 번만 표시된다.
- 판단 실수로 진행이 영구적으로 막히지 않는다.

### F-06 업체 자격 검증

- 담당: 팀원 1(`ProcurementSystem.checkEligibility()`)
- 화면: 팀원 3
- 기준: 기획서 4·5.2·8장

**데이터**

- 고정 공급업체 3곳과 사전 작성된 제안

**필수 조건**

하나라도 충족하지 못하면 부적격이다.

- 제안 금액이 사업 예산 안에 있어야 한다.
- 필수 규격을 충족해야 한다(F-04에서 추가된 규격 포함).
- 계약 수량을 공급할 수 있어야 한다.
- 필요한 시점까지 납품할 수 있어야 한다.

**규칙**

- 부적격 업체는 비교 점수와 관계없이 계약 대상이 될 수 없다.
- 부적격 사유를 표시한다.
- 플레이어가 필수 규격이나 자격 기준을 임의로 변경하는 기능은 없다.

**미정**

- 업체 3곳의 구체 데이터

**완료 조건**

- 각 필수 조건을 하나씩 위반한 업체가 해당 사유로 부적격 처리된다.
- 3곳 중 적격 업체가 최소 하나 존재한다.

### F-07 제안 비교

- 담당: 팀원 1(`ProcurementSystem.compareSuppliers()`)
- 화면: 팀원 3
- 기준: 기획서 4장 판단 포인트 '제안 비교'

**동작**

- 적격 업체만 가격, 품질(규격 충족 정도), 납기로 비교해 순위를 매긴다.
- 각 항목의 비교 결과와 순위 판단 근거를 표시한다.

**규칙**

- 가격만으로 업체를 판단하지 않는다.
- 플레이어가 업체를 임의로 지정하지 않는다.
- 결과는 공개된 비교 기준에 따라 결정된다.
- 동일한 입력에는 항상 동일한 결과가 나와야 한다.

**미정**

- 비교 가중치
- 품질 값의 척도

가격 40·품질 40·납기 20은 초기 검토안이며 확정된 값이 아니다.

**완료 조건**

- 부적격 업체는 비교 순위에 포함되지 않는다.
- 같은 입력이면 항상 같은 순위가 나온다.
- 비교 항목별 결과를 확인할 수 있다.

### F-08 계약 체결과 예산 차감

- 담당: 팀원 1(`ProcurementSystem.createContract()`)
- 화면: 팀원 3

**동작**

플레이어가 비교 결과를 확인하고 계약을 확정하면 1순위 업체와 계약한다.

**처리 순서**

1. 사업 단계가 `REVIEWING`인지 확인한다.
2. 선택한 업체가 1순위인지 확인한다.
3. 예산을 차감한다(`GameState.spendBudget()`).
4. 계약 정보를 저장한다(`GameState.setContract()`).
5. 사업 단계를 `CONTRACTED`로 변경한다.
6. 결과 이벤트 `CONTRACT_CREATED`를 발생시킨다.

**예외**

- 예산 부족: 계약하지 않고 `CONTRACT_REJECTED`를 발생시킨다. reason은 `INSUFFICIENT_BUDGET`이다.
- 이미 계약된 상태: 계약을 다시 진행하지 않고 `INVALID_STATE`를 반환한다.
- 부적격 업체나 2순위 업체는 계약할 수 없다.

**규칙**

- 계약 금액은 계약 체결 시 한 번만 차감한다.
- 납품·검수 단계에서 계약 금액을 다시 차감하지 않는다.

**완료 조건**

- 계약 버튼을 두 번 눌러도 예산은 한 번만 차감된다.
- 예산이 부족하면 계약이 거부된다.
- 부적격 업체나 2순위 업체와 계약되지 않는다.
- 계약 정보와 사업 단계가 일치한다.

## 4. 2월차: 납품, 검사, 평가

### F-09 납품 진행

- 담당: 팀원 1(`DeliverySystem.start()`)
- 화면: 팀원 2(지역·월드 표현), 팀원 3(관청 UI)

**동작**

- 2월차 업무 진행이 시작되면 계약된 사업의 납품을 시작한다.
- 사업 단계가 `DELIVERING`으로 변경된다.
- 공방의 완제품 재고·제작·운송 상태가 납품 흐름에 맞게 바뀐다.

**규칙**

- 계약된 사업만 납품을 진행할 수 있다.
- 근거 없는 무작위 지연은 만들지 않는다.
- 납품 진행은 계약 정보를 기준으로 처리한다.

**완료 조건**

- 계약 없이 납품 상태로 전환되지 않는다.
- 납품 시작 후 사업 단계와 납품 상태가 일치한다.

### F-10 일부 납품 사건

- 담당: 팀원 1(사건 처리)
- 화면: 팀원 3
- 기준: 기획서 4장 '가벼운 사건'

**동작**

1. 공방의 완제품 재고가 부족해 침구 일부만 먼저 납품된다.
2. 진행이 멈추고 플레이어에게 대응을 요청한다(F-03).
3. 플레이어는 계약 수량과 실제 납품 수량을 확인한다.
4. 공방과 나머지 납품 일정을 협의한다.
5. 누구에게 먼저 지급할지 요청기관과 확인한다.
6. 두 가지 대응을 마치면 나머지가 납품되고 진행이 이어진다.

**규칙**

- 이 사건은 실패가 아니라 보완 과정이다.
- 정해진 기한 안에 해결하면 평가에 불이익이 없다.
- 시나리오에 정해진 사건이며 무작위로 발생하지 않는다.
- 공방의 재고 부족은 기업 사정이다. 기관의 계약 준비 지연과 혼동하지 않는다.

**결과 이벤트**

- `DELIVERY_ISSUE_FOUND`
- `DELIVERY_ISSUE_RESOLVED`

**미정**

- 먼저 납품되는 침구 수량

**완료 조건**

- 사건 대응 중에는 다음 달로 넘어가지 않는다.
- 두 가지 대응을 모두 마치면 나머지 물품이 납품된다.
- 최종 실제 납품 수량이 품목별 검사 목표(`max(계약 수량, 실제 필요 수량)`) 이상이다.

### F-11 현장 검사와 사용 개시

- 담당: 팀원 1(`DeliverySystem.inspect()`)
- 화면: 팀원 2(지역·월드 표현), 팀원 3
- 기준: 기획서 4장 '사용 개시', 5.2

**동작**

1. 검사·검수 책임 주체가 요청기관임을 표시한다.
2. 계약 수량·규격과 실제 납품 결과를 비교한다.
3. 남은 물품이 도착하면 사업 단계가 `INSPECTING`으로 변경된다.
4. 플레이어가 검사 결과를 확인한다.
5. 검사 통과 후 성과평가(F-12)로 이어진다.

**예외**

- 필수 조건을 충족하지 못하면 검사 결과와 사유를 표시한다.
- 미충족 상태에서는 사업을 완료 처리하지 않는다.
- 점검 생략으로 부족 수량을 잘못 확정한 경우 기존 TEMP 보완 납품을 실행하고, 보완 예산과 실제 최종 납품 수량을 반영해 정식 검사한다. 품목별 검사 목표는 `max(계약 수량, 실제 필요 수량)`이며, 최종 실제 납품 수량이 목표 이상이어야 한다. 계약 수량은 보완 때문에 변경하지 않는다. 보완 실패나 예산 부족 시 명령 전체를 명령 직전 snapshot으로 되돌린다.

**결과 이벤트**

`INSPECTION_COMPLETED { passed, findings }`

**TEMP**

- 점검을 생략해 계약 수량이 실제 필요 수량보다 적으면 실제 부족분을 같은 업체의 보완 납품으로 채운다. 보완 물품의 단가·비용 산정은 `src/data/suppliers.js`를 따른다. 정식 검사 결과는 보완 후 실제 납품 수량과 규격으로만 판정한다.

**완료 조건**

- 계약 수량 이상 및 실제 필요 수량 이상을 모두 충족한 납품은 통과할 수 있으며, 계약 수량을 초과한 납품도 허용한다.
- 규격을 충족하지 못한 납품은 정상 통과하지 않는다.
- 검사 결과가 이후 평가 단계에 반영된다.

### F-12 성과평가

- 담당: 팀원 1(`EvaluationSystem.calculateGrade()`)
- 화면: 팀원 3
- 기준: 기획서 5.3, 9장

**동작**

- 품질: 규격 충족과 사용 적합성
- 기한: 필요한 시점까지 공급했는지
- 절차: 정해진 기준과 기록을 지켰는지

각 항목을 판정하고 S~D 종합 등급과 핵심 이유 한 문장을 표시한다. 보완해서 바로잡은 과정도 기록한다. 평가가 완료되면 사업 단계가 `EVALUATED`로 변경된다.

**규칙**

- 첫 버전의 종합 등급은 S~D만 사용한다.
- 신뢰도 지표와 혼합하지 않는다.
- 예산 효율은 평가하지 않는다.
- 상세 점수와 등급 산출 공식은 첫 버전 범위에서 제외한다.

**결과**

- S~C 등급은 평가 통과로 보고 추가 정원 1명을 승인한다(`HEADCOUNT_APPROVED`).
- D 등급은 미통과이며 시설 개선·추가 정원 승인·후보 생성·채용을 차단한다. 평가와 보완 안내를 보여준 뒤 튜토리얼을 종료한다.
- 평가의 `passed`는 등급 정책과 일치해야 한다.
- 평가 결과와 등급을 GameState에 저장한다.

**미정**

- 항목별 판정 표시 형식
- S~D 종합 등급 산출 공식과 등급 경계
- D 도달 조건과 등급 산출 공식은 TEMP로 유지한다. 미통과 이후에는 시설 개선·추가 정원 승인·모집을 보류하고 튜토리얼을 종료한다.

**완료 조건**

- 같은 평가 결과에는 같은 등급이 나온다.
- 등급은 S~D 범위 안에서 결정된다.
- 핵심 평가 이유를 확인할 수 있다.
- 평가 결과가 GameState에 반영된다.

### F-18 자동 저장 (P1)

- 저장·복원 로직: 팀원 1; 저장 실패 상태 표시 UI: 팀원 3(`UIScene`)
- 기준: 기획서 3장 '저장'

**동작**

- 저장 시점: 새 게임을 시작하면 기존 저장 데이터를 새 게임 상태로 교체한다. 이후 게임 진행 명령(`store.dispatch`)이 성공할 때마다 변경된 상태를 `localStorage` 단일 슬롯에 자동 저장한다. 월초·월말 전환도 해당 명령이 성공하면 저장된다.
- 실패·롤백된 명령과 `ROLLBACK_FAILED` fatal 상태는 저장하지 않는다. 마지막 정상 저장이 유지된다.
- 수동 저장은 제공하지 않는다.
- GameState의 `toJSON()`으로 저장 데이터를 만들고 `load(saved)`로 복원한다.
- 저장 데이터에는 버전을 포함한다.
- 후보 목록(F-14), 안내 이력 및 설정(F-15)은 해당 명령이 성공하면 즉시 저장한다.

**복원 기준**

- 새로고침하면 마지막으로 성공한 명령 이후의 상태로 복원한다. 월 중간이면 월중 진행 상태(예: 일부 납품 대응 중)를 그대로 복원한다.
- 복원은 저장된 상태를 불러올 뿐 명령을 다시 실행하지 않는다. 계약 예산 차감, 평가, 채용 등 이미 처리된 결과는 중복 적용되지 않는다.

**규칙**

- 저장 데이터가 없거나 손상되었거나 버전이 맞지 않으면 초기 상태로 시작한다. 손상·버전 불일치 데이터는 폐기한다.
- 저장에 실패하면 성공한 것으로 표시하지 않으며, `TYCOON.app.saveStatus`에 실패 상태를 노출한다. 게임 진행은 계속한다.
- 저장 실패 후 저장이 가능해지면 다음 성공 명령에서 다시 저장을 시도한다.
- GameState의 `toJSON()`과 `load()`는 저장 데이터 직렬화·복원 기능이다. 브라우저 `localStorage`에 실제로 기록하고 읽는 기능과는 구분한다.
- 유효한 저장이 있으면 새로고침 후 사무실과 UI를 자동으로 재개하고, UI 단계는 복원한 GameState와 meta에서 구성한다.

**현재 상태**

- GameState 저장 형식(`toJSON`, `load`): 구현
- 브라우저 `localStorage` 연동: 구현(`src/core/BrowserSave.js`, 단일 슬롯, 자동 복원)

**완료 조건**

- 새 게임 시작 시 기존 저장 데이터가 새 게임 상태로 교체된다.
- 성공한 명령 뒤에는 저장되고, 실패한 명령 뒤에는 이전 저장이 유지된다.
- 월 중간에 새로고침하면 마지막으로 성공한 명령 이후의 상태로 복원된다.
- 같은 저장 데이터를 여러 번 복원해도 결과가 같다.
- 이미 차감된 계약 예산과 평가·채용 결과가 중복 적용되지 않는다.
- 후보 목록과 선발 결과가 복원된다.
- 안내 이력과 설정이 복원된다.
- 저장 데이터가 없거나 손상된 경우 초기 상태로 시작한다.
- 저장 실패를 성공으로 표시하지 않고, 게임 진행을 막지 않으며, 다음 성공 명령에서 저장이 회복된다.

### F-19 실행파일과 제출 ZIP

- 담당: 팀원 1
- 상태: 연결 파일과 제출 도구 구현, Pages 실제 배포는 저장소 생성 후

**동작**

- 게임 본체 `index.html`은 GitHub Pages로 배포한다.
- 제출용 `게임실행.html`은 Pages 주소로 연결한다.
- `실행안내.txt`와 함께 ZIP으로 제출한다.
- 개발 중에는 `index.html`을 더블클릭해 실행한다.

**규칙**

- 제출 후 심사가 끝날 때까지 `main`(배포 브랜치)을 변경하지 않는다.
- 인터넷이 안 되는 경우를 대비해 오프라인 실행본을 함께 넣는 것을 권장한다.

**완료 조건**

- 다른 PC에서 ZIP을 풀고 `게임실행.html`을 더블클릭하면 Pages의 게임이 열린다.
- 실행 중 페이지 오류가 발생하지 않는다.
- 오프라인 실행본을 포함했다면 인터넷 연결 없이도 실행된다.

## 7. 첫 버전에서 만들지 않는 것

기획서 3장 '후속 확장으로 미룸'과 7장 로드맵에 있는 기능은 첫 버전에서 구현하지 않는다. 잠긴 메뉴로도 표시하지 않는다.

- 칸막이·수납함, 학당 책상, 다리 복구 등 다음 사업
- 월중 결재, 추가 지원 신청
- 예산 효율 평가, 상세 등급 체계
- 인재 명부, 모집권, 직원 성장·교육·피로
- 기관 운영비, 시설 확장
- 수동 저장
- 전투, 레벨·경험치·스킬, 캐릭터 자유 이동

## 9. 미정 항목

기획에서 정하기 전까지 임의로 정하지 않는다. 동작 확인을 위한 임시값은 설정·데이터 파일 한 곳에 모으고 `TEMP`로 표시한다. 규칙 코드에 숫자를 직접 작성하지 않는다.

| 항목 | 관련 기능 | 정할 사람 |

| 연령 구성, 사용자 규격 확인 결과 | F-04 | 기획 |
| 먼저 들어오는 침구 수량 | F-10 | 기획 |

| 초기 예산 | F-08 | 기획·팀원 1 |
