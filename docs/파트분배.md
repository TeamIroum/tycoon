# 조달청 타이쿤 — 팀원별 업무 분배 및 개발 계획

## 1. 프로젝트 개요

| 항목 | 내용 |
|---|---|
| 프로젝트 | 조달청 타이쿤 |
| 개발 인원 | 3명 |
| 게임 엔진 | Phaser 3.80.1 |
| 언어 | JavaScript, HTML, CSS |
| 플랫폼 | PC 웹 브라우저 |
| 해상도 | 1280×720 |
| 구조 | IIFE, 전역 `TYCOON`, `file://` 직접 실행 |

현재 구현과 미완료 기능은 `docs/기능정의서.md`를, 게임 정책은 `docs/게임기획서.md`와 `docs/기능정의서.md`를 기준으로 확인한다.

### 업무 분배 원칙

- 담당자는 자신이 소유한 기능과 파일의 구현·검증을 책임진다.
- 공통 구조와 API는 팀원 1이 관리한다.
- UI와 Scene은 표시와 사용자 입력을 담당하고, 게임 규칙은 담당 System에서 처리한다.
- 타 팀원 소유 파일은 사전 협의 없이 수정하지 않는다.
- 미확정 기획과 밸런스를 임의로 확정하지 않고 `TEMP`로 유지한다.

## 2. 팀원별 담당 업무

### 팀원 1 — 황상진: 핵심 시스템 및 통합

**담당 기능:** F-01~F-14의 핵심 규칙(기존 ID 유지), F-18, F-19 및 전체 통합

**담당 파일:**

```text
src/main.js
src/config/* (except `src/config/assets.js`)
src/core/*
src/systems/*
src/data/projects.js
src/data/suppliers.js
src/data/facilities.js
src/systems/TutorialFlow.js
src/scenes/BootScene.js
src/scenes/PreloadScene.js
src/scenes/TitleScene.js
tools/*
submission/*
```

**주요 책임:** GameState/schema, 공통 API·이벤트·Store, 진행 흐름과 롤백, 조달·계약·납품·검사·평가·시설 상태·채용 로직, 저장·복원, 통합 및 테스트를 담당한다. 규칙과 상태 변경은 팀원 1이 소유하며 월드·UI 담당자는 규칙을 복제하지 않는다.

### 팀원 2 — 이현우: 게임 에셋 및 월드 표현

**담당 기능:** 기존 F-02·F-13 등에서 지역·시설의 시각 표현 부분. 기능 ID와 게임 규칙 소유권은 바꾸지 않는다.

**기존 담당 파일:**

```text
src/ui/art.js
src/scenes/VillageScene.js
src/scenes/HallScene.js
```

**담당 파일:** `src/config/assets.js` 전체 — 에셋 등록, 경로 관리 및 리소스 설정. **예정 에셋 경로(현재 미존재):** `src/assets/**` — 캐릭터·건물·시설·배경·타일 등 신규 아트 리소스.

**주요 책임:** 2D 쿼터뷰 픽셀 아트 스타일, 마을 배경·지형·타일맵, 시설 배치와 월드 오브젝트, 게임 진행에 따른 배경·시설 외형 변화를 담당한다. `src/config/assets.js`에서 에셋 등록·경로·리소스 설정도 전담한다. Scene의 공통 게임 상태 변경은 기존 Store/TutorialFlow API 계약을 사용한다.

### 팀원 3 — 이소미: UI/UX 및 화면 연출

**담당 기능:** F-15~F-17 및 모든 기능의 UI 표현 부분

**담당 파일:**

```text
src/scenes/OfficeScene.js
src/scenes/UIScene.js
src/scenes/EndingScene.js
src/ui/widgets.js
src/ui/viewData.js
src/ui/MascotDialog.js
src/data/dialogs.js
```

**주요 책임:** `OfficeScene.js` 전체를 포함한 관청 화면 구현, 사용자 입력, 화면 내 동작 및 관련 상태 변경 코드와 HUD·패널·튜토리얼·화면 연출을 담당한다. `OfficeScene.js`는 팀원 3 단독 소유이며 팀원 1과 공동 소유하지 않는다. 공통 GameState 변경 및 게임 규칙은 기존 Store/TutorialFlow API 계약을 통해 처리하며 API 계약 자체는 변경하지 않는다.

**파일 소유권 원칙:** 각 파일은 표에 명시한 한 팀만 소유한다. `src/ui/art.js`, `src/config/assets.js`, `VillageScene.js`, `HallScene.js`, `src/assets/**`는 팀원 2 소유이며 `OfficeScene.js`, `UIScene.js` 및 나머지 UI·엔딩 파일은 팀원 3 소유다.

## 3. 기능 ID 연결

| 담당 | 기능 |
|---|---|
| 팀원 1 | F-01~F-14 게임 규칙, F-18 자동 저장·복원, F-19 제출 파일/패키징 |
| 팀원 2 | F-02, F-09, F-11, F-13의 배경·시설·월드 시각 표현 및 에셋 전반 |
| 팀원 3 | F-01~F-18의 UI 표시·입력·튜토리얼 안내·엔딩 표현 |

F 번호별 완료 기준과 예외 동작은 `docs/기능정의서.md`를 따른다. F-14의 후보 데이터·선발 규칙은 팀원 1, 선택 화면은 팀원 3, 저장·복원은 팀원 1이다.

## 4. 공통 API 및 데이터 관리

세부 API 계약은 `docs/API명세서.md`를 따른다. GameState·Store·TutorialFlow·공통 이벤트/결과와 모든 게임 규칙은 팀원 1, 월드·에셋 표현은 팀원 2, 화면 입력·UI·대사는 팀원 3이 소유한다.

```text
Scene / UI → store.dispatch(command) → TutorialFlow → 담당 System → GameState → 이벤트 → 화면 갱신
```

System 결과는 `{ ok: true, ... }` 또는 `{ ok: false, reason: '...' }`를 따른다. System을 직접 호출하거나 GameState를 직접 변경하지 않는다. 공통 API·schema·이벤트·GameState 변경은 사전 협의 후 API 명세와 관련 테스트를 함께 갱신한다.

## 5. 파일 소유권과 협업 경계

공통 영역은 팀원 1 소유다.

```text
index.html
src/main.js
src/config/* (except `src/config/assets.js`)
src/core/*
tools/*
submission/*
```

담당 외 파일을 수정해야 하면 해당 파일 소유자와 먼저 협의한다. 공통 API·GameState·규칙 계약 변경은 팀원 1 및 관련 소비자와 협의한다. 월드 Scene과 공통 상태의 연동은 팀원 1·2가, UI 동작과 공통 API 연동은 팀원 1·3이 협의한다. `src/config/assets.js` 및 `src/assets/**`의 에셋 작업은 팀원 2의 소유 범위이며 별도의 팀원 1 승인 대상이 아니다.

## 6. 개발 및 통합 절차

1. 기획·기능·API 문서와 기존 코드를 확인한다.
2. 담당 범위, 공통 API 영향, 파일 충돌 가능성을 정리한다.
3. 필요한 협의와 승인을 거친 뒤 최소 변경으로 구현한다.
4. 관련 단위·통합·브라우저 테스트를 실행한다.
5. 미실행 테스트와 남은 위험을 구분하여 보고한다.
6. 모든 팀원은 개인 개발 브랜치 `team1`, `team2`, `team3`에서 작업하고 `develop` 대상으로 PR을 만든다. 팀원 1이 검토·병합하고 `develop`에서 통합 테스트와 오류 수정을 관리한다. 안정화 후 `develop`에서 `main`으로 PR을 만든다. `main`과 `develop` 직접 푸시는 금지한다. 상세 절차는 `docs/GitHub_팀원_협업가이드.md`를 따른다.

## 7. MVP 범위와 TEMP 관리

첫 버전은 튜토리얼과 첫 동료 선발까지다. 다음 사업, 직원 성장·교육·피로, 상세 점수 체계 등 후속 시스템을 임의로 추가하지 않는다.

확정 검사 정책은 검사 목표 `max(계약 수량, 실제 필요 수량)`, 최종 실제 납품 수량 목표 이상, 프로젝트 필수 규격 충족이다. 점검 생략 경로는 계약 12개·필요 14개·보완 2개·18만 원·최종 14개다. 계약금과 보완 비용은 분리한다. S~C 통과, D 미통과 정책을 유지한다.

비교 가중치, 평가 공식과 등급 경계, D 도달 조건, 일부 부족량·부분 납품 수량, 후보 생성 규칙과 수치는 TEMP다. 테스트용 임시값을 최종 기획 정책으로 표현하지 않는다.

## 8. 테스트 기준 및 완료 조건

기록된 QA 기준은 Node 자동 테스트 60개, Chromium CDP 4개 경로, UI E2E 10개 시나리오 통과다. Chrome headful 전체 시나리오 통과 기록과 Edge 개별 통과를 구분하며, Edge 전체 연속 실행은 불안정해 PASS로 간주하지 않는다.

```powershell
& 'C:\Program Files\Microsoft Visual Studio\18\Community\MSBuild\Microsoft\VisualStudio\NodeJs\Node.exe' tests/all.mjs
& 'C:\Program Files\Microsoft Visual Studio\18\Community\MSBuild\Microsoft\VisualStudio\NodeJs\Node.exe' tests/browser/chromium-cdp.mjs
& 'C:\Program Files\Microsoft Visual Studio\18\Community\MSBuild\Microsoft\VisualStudio\NodeJs\Node.exe' tests/browser/play-walkthrough-cdp.mjs
```

기능 작업은 관련 테스트를 실행하고 기존 테스트의 기대값만 바꿔 통과시키지 않는다. UI 입력 검증은 실제 입력과 dispatch 기반 테스트를 구분해 보고한다. 완료 보고에는 수정 파일, 변경 내용, 실행 명령과 실제 결과, 미해결 사항을 기록한다.

## 9. GitHub 브랜치 및 PR 정책

| 브랜치 | 용도 | 담당 |
|---|---|---|
| `main` | 안정화된 최종 버전 및 공모전 제출 | 황상진, 팀원 1만 최종 병합 |
| `develop` | 팀별 작업 통합 및 테스트 | 황상진, 팀원 1이 PR 검토·병합 |
| `team1` | 황상진 개발 브랜치 | 황상진 |
| `team2` | 이현우 개발 브랜치 | 이현우 |
| `team3` | 이소미 개발 브랜치 | 이소미 |

최종 병합 흐름은 `team1 / team2 / team3 → develop → main`이다. 팀원은 자신의 개발 브랜치에서 `develop` 대상 PR을 생성하고 팀원 1이 검토·병합한다. 통합 테스트와 오류 수정은 `develop`에서 검증하며 수정은 담당 브랜치의 PR로 반영한다. 안정화 후 팀원 1이 `develop`에서 `main` 대상 PR을 생성·병합한다. `main`과 `develop` 직접 커밋·push는 금지한다. 기존 `team4` 브랜치는 사용하지 않는다. force push, 타 팀원 브랜치 변경·삭제, 인증 정보 커밋은 금지한다. GitHub 권한과 branch protection/ruleset 적용 여부는 별도 확인한다. 자세한 절차는 `docs/GitHub_팀원_협업가이드.md`를 따른다.
## 10. AI 도구 사용 원칙

- 관련 기획·기능·API 문서와 현재 구현을 먼저 확인한다.
- AI가 제안한 코드와 API가 실제 프로젝트에 맞는지 담당자가 직접 검토하고 실행한다.
- 요청하지 않은 구조 변경과 기능 추가를 하지 않는다.
- 미확정 기획이나 밸런스를 임의로 결정하지 않는다.
- 테스트하지 않은 동작을 완료로 보고하지 않는다.
- 변경 파일, 영향, 테스트 결과와 미해결 위험을 공유한다.
